Scope: `internal/http/provisioning_chat_runner.go`, `provisioning_chat_stream.go`, their tests; read-only cross-check of `provisioning_chat.go`, `provisioning_chat_abort.go`, `agent/router.go`, `gateway/methods/chat.go`, `http/chat_completions.go`. ## Verified OK
- Registration parity: `provisioning_chat_runner.go:48-56` = `gateway/methods/chat.go:444-460` (WithoutCancel, then InjectTeamDispatch, then WithCancel, then RegisterRun on the base ctx so TenantID is captured). `InjectCh` (:67) and `OnTraceCreated`→`SetRunTraceID` (:68-70) are wired. `defer UnregisterRun` and `defer cancel` cover the success, error and panic paths. `router.Get` failure returns before RegisterRun, so nothing leaks. A fence rejection in RegisterRun cancels and closes injectCh, the same as the other callers.
- Boundedness: the run ends on loop completion, router abort or process exit. It is the same as `chat.send`: no wall-clock cap (already noted by the implementer). No goroutine leak: the handler goroutine stays pinned until the run returns, then exits. No http.TimeoutHandler or request-ctx timeout wraps this route (grep: none in `internal/http`).
- Write after return: OnEvent runs synchronously inside `RunWorkspaceChat`, and parallel tool goroutines are joined (`pipeline/tool_stage.go:275` WaitGroup) before return, so nothing writes after the handler returns. A write in the TOCTOU window between the `done` check and `Fprintf` (`stream.go:78-88`) goes to a still-live handler's ResponseWriter and just returns an error. That is safe.
- Setup-turn side effects survive disconnect: the lease uses WithoutCancel (`provisioning_chat_setup_turn_lease.go:59`) and `markSetupHandoff` uses WithoutCancel (`provisioning_chat_setup_turn.go:142`).
- Bug 1: the loop emits `map[string]string` (`agent/loop_pipeline_callbacks.go:430,443,573,588,600`, `loop_pipeline_adapter.go:318,329`), and `chunkContent` handles both shapes.
- Tests would fail without the fix: the mapper cases for `map[string]string` return ""; `RegistersRunForStatusAndAbort` fails because `IsSessionBusy` returns false; `SurvivesRequestCancel` fails because cancel propagates synchronously, so ctxErr=Canceled whichever select branch wins. Channel handoffs make them race-free.

## Should-fix
S1. The buffered (non-stream) path maps a user abort to HTTP 500 plus a retry hint. `provisioning_chat.go:286-300`.
  Scenario: the CCP sends `stream:false`, the user hits Stop, and `/workspace-chat/abort` cancels the run. `loop.Run` returns a ctx error, which `ClassifyWorkspaceChatRecovery` maps to `runtime_request_failed`/`retry`, so the caller gets a 500 "request failed, retry" and may auto-resend the turn the user just stopped. Before #991 this path was unreachable, because runs were not registered.
  Fix: when `errors.Is(err, context.Canceled)` (or the runner surfaces "aborted"), return 200 with `{stopped:true}` or 409 with a dedicated code. Skip `setupTurn.runFailed` on an abort, or pass the abort to it explicitly.
S2. On the stream path, a setup turn that is aborted can emit two terminal frames. `provisioning_chat_stream.go:121-128,155-166`.
  Scenario: the run is aborted after `OnInputDelivered`. `chat.stopped` is sent immediately (it is not held), then `runFailed(true)` sets `delivered`, so a second `chat.error setup_result_delivered` follows. Clients that end the stream on the first terminal frame drop the second, and others render an error after "stopped". Fix: when `terminalSent` came from `chat.stopped`, do not send the delivered error, or hold `chat.stopped` the same way `chat.error` is held.
S3. There is no busy guard before starting a run on an existing session. `provisioning_chat.go:218-232` (compare #956 `extension_api_chat.go:102`).
  Scenario: the client disconnects (the run continues, by design), reconnects and resends the turn. Two concurrent runs then write the same session history. `RegisterRun` overwrites `sessionRuns[key]` (`router.go:344`). When the first run finishes, `UnregisterRun` deletes the index unconditionally (`router.go:365`), so status reports "idle" while run 2 is still streaming. Fix: return 409 when `IsSessionBusy(sessionKey)`, matching the extension route. Optionally make `UnregisterRun` delete only when the index still points to its own runID (CompareAndDelete).
S4. (Pre-existing, now reaches workspace runs; file a separate `security` issue.) The router indexes runs by session key across all tenants. WS `chat.abort`/`chat.sessionStatus` let any tenant admin skip the session check (`gateway/methods/access.go:30`, `chat.go:93-101,746-766`, `AbortRun(runID,"")`). A tenant-A admin who knows a tenant-B workspace session key or runID can read B's run state or abort B's run. Exploiting it needs the key: `agent:{key}:app:direct:{user}-{8 hex}` has a 32-bit random suffix, and run IDs are UUIDv4. The provisioning abort route itself is tenant-scoped (`provisioning_chat_abort.go:121-130`). Fix: store TenantID in `ActiveRun` (already captured) and require it to match in `AbortRun`/`SessionRunID`/abort-by-runID.
S5. (Pre-existing, separate issue.) `sseEventWriter` is not safe for concurrent use, yet `tool.call` is emitted from parallel tool goroutines (`agent/loop_pipeline_tool_callbacks.go:123` via `pipeline/tool_stage.go:278`). This contradicts the OnEvent invariant at `loop_types.go:804-813`. Scenario: two parallel-eligible tools produce interleaved `Fprintf`/`Flush` calls on one ResponseWriter, which is a data race that can corrupt SSE frames. #991's `done` read is race-free, but it does not address this. Fix: add a mutex in `send`.
S6. The tests do not cover the handler wiring. No test drives `handleProvisionWorkspaceChatStream` with a cancelled `r.Context()` to prove (a) the run completes and (b) no frames follow. A regression to `newSSEEventWriter(w, nil)` or to a non-detached runner in the handler would pass the suite. Add one httptest case using `req.WithContext(cancelCtx)` and a blocking fake runner.

## Nit
N1. `chunkContent` (`stream.go:278`) duplicates `channels.extractPayloadString` (`channels/events.go:687`). This is acceptable across packages; mention it in a comment or move it to a shared helper later.
N2. Defer order: `drainTeamDispatch` runs after `UnregisterRun` (`runner.go:50,56`), so status shows idle while post-turn team dispatch is still running. `chat.go:458-460` does the reverse, and `chat_completions.go` matches #991. Pick one order.
N3. The comment at `runner.go:46-47` says the run is stopped "only by the router abort". A tenant-transfer fence in `RegisterRun` also cancels it.
