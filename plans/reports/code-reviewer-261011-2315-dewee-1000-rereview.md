## Nit
1. **Log volume and noise.** See router_tenant_scope.go:31-34.
   - The WARN `security.cross_tenant_run_access_denied` fires on every lookup that hides a run. One `chat.status` probe can emit up to 3 WARN lines, plus more for each run session (chat.go:97-137).
   - Any member can trigger these at will, so the log can be flooded, though only at the rate of their own requests.
   - Benign collisions on channel keys (the same peer, channel name and agent key in two tenants) will also produce "security" warnings.
   - Consider logging once per request, or at Info level for status and busy probes.
2. **Logging the session key is acceptable.**
   - It is an identifier, not a secret, and the code already logs it elsewhere (for example the wake.go "wake request" log and related.go:45).
   - On client paths the caller supplied the key, so the log discloses nothing new.
   - Channel keys embed the platform peer or chat ID, which is pseudonymous PII. That matches the existing logging practice.
   - No message content, tokens or credentials are logged.
3. **The call-site swaps in cmd/gateway_consumer_normal.go and the injection at chat.go:428 have no direct handler tests.** They are covered only by the router-level helper tests. The risk is low because the swaps are mechanical one-liners.
4. **Every chat.send that reaches `Prepare` with no active context now scans `activeRuns` in full.** This happens when the index misses, which is the common idle case (router_tenant_scope.go:56-72). It is O(active runs), which is fine at the current scale. The scan is needed for correctness until dewee#1008 keys the index by tenant.
5. **The commit and PR text do not mention the owner-role behaviour change.** A system owner can no longer abort or inspect runs in other tenants through chat.abort or chat.status. Add one line to the PR body.
6. **Rebase onto the current origin/dev before merge.** The branch is 11 commits behind, and the stale merge-base is what makes `TestGetForRunEvicts…` fail locally.
